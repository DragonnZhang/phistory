# 95-agent Phistory integration audit

Current verified runtime coverage is **56/95**: the original 12 plus 44 newly integrated projects, each with a real Linux request and an independent fresh capture. The other 39 remain source archives or pending native runtime work. New snapshots preserve complete emitted request bodies and tool schemas for their explicitly named entry points; stage/example/API captures do not represent every application role or later pipeline stage. Original source-file archival is complete for all 83 new targets, with 366 original files and hash evidence, and stays separate from runtime capture.

Latest verification includes [Raven and ZCode](https://github.com/DragonnZhang/phistory/actions/runs/44103166713), [CowAgent](https://github.com/DragonnZhang/phistory/actions/runs/44102837808), and [BambooAI and AgenticSeek](https://github.com/DragonnZhang/phistory/actions/runs/44104927439). Native tool counts are 32, 24 and 18 for the first three; BambooAI and AgenticSeek use their native text/code protocols with zero JSON tools. CowAgent's only tool-definition variation is the actual isolated workspace path in its bash description; raw values are retained. Its default memory is native keyword search when no embedding provider is configured. The chronological sections below retain earlier milestones and initial source-only hypotheses; current runtime support is determined by these verified captures and the registry's latest policy.

The survey names 95 repositories, including terminal CLIs, configurable applications, research scripts, and outer orchestration systems. The starting Phistory registry already covers 12; these are skipped. The other 83 belong in a separately identified source archive immediately, with request-capture drivers added where a reproducible entry point is available. A source snapshot contains real upstream file bytes, not an emitted API request. It must not be labeled `trace.jsonl` or described as a resolved runtime system prompt/toolset.

The table distinguishes the initial registry overlap from new source targets. “CLI candidate” means an official executable/source entry exists; it does not claim a Linux capture succeeded. The exact commits and content hashes belong to `phistory/source_catalog.json`. Source references below point to pinned upstream evidence, and README references identify the official installation/entry documentation.

## Source-surface repairs

The initial survey citations often selected a short discriminating fragment rather than the full prompt assembly surface. Source archival therefore includes the following additional pinned upstream files:

- Goose: base `prompts/system.md`, subagent template, prompt manager and template registry, alongside the developer extension. Extension instructions are not the whole system prompt.
- Agent Zero: the root `agent.system*.md` family, their small Python template providers, and plugin system/tool prompt templates. The solving section alone omits identity, environment, communication, skills and tool instructions.
- Fibona: `core/agent.py` carries both `INSTRUCTIONS` and the `SET_NEXT_CELL` schema. Terminal `context.py` adds developer-role working instructions; minimal bootstrap is separate.
- Prime Agent: core/usage/opinionated/model layers, system-prompt assembler and the native `ipython_tool_schema` implementation. REPL programmatic tool guidance and API tool schema are distinct artifacts.
- AutoResearchClaw: MCP tool schema registry and code-agent adapter, with explicit external-CLI boundaries.
- RobotUse: native tool registry, schema and discovery code; physical/simulator environments remain a runtime condition.
- TrashClaw: the same source file contains both prompt assembly and the `TOOLS` declarations.
- Skyvern: action model definitions and action types accompany action prompt templates; these are the actual structured action surface, not a generic native function-tool claim.

LibreChat and DeepAnalyze do not have a universal built-in system prompt to export for every deployment. Archive their configuration/assembly code and preserve that distinction. Likewise, external CLI tools used by LongHorizon, Dark-Moon, LoopTroop or AutoRef are not declared to be the outer project's own universal toolset.

All real execution captures and fresh smoke runs belong in Linux GitHub Actions. Source-file download, hashing, rendering and fake-CLI tests can run locally; neither an installable package nor a checked source hash is evidence that a runtime request capture passed.

### Shared claude-tap protocol requirement

At the pinned tap revision, `clients.generic(cmd)` advertises only `PASSTHROUGH`. Request export can later infer the provider from the raw request, but dummy-response generation and streaming detection select their behavior from the already chosen `Protocol`. Consequently, a generic Chat Completions or Anthropic child currently receives a Responses-shaped fallback dummy and may retry or hang.

The shared correction is to give generic clients `(ANTHROPIC, OPENAI, GEMINI, PASSTHROUGH)`, in that order with catch-all last. This reuses typed path selection, JSON/SSE dummy generation and streaming detection in both forward and reverse transports. Six duplicate client definitions are unnecessary. Native `/v1/messages`, `/v1/responses`, `/v1/chat/completions` and Google model paths are covered; the existing OpenAI `suffix:/chat/completions` rule also covers OpenRouter's `/api/v1/chat/completions`. Startup GETs and arbitrary gateway paths remain separate concerns: catch-all dummy output is not a model catalog/auth bootstrap implementation. [Generic client](https://github.com/DragonnZhang/claude-tap/blob/64872f527b862906b5944e74b4d155e6cbb4bd44/claude_tap/clients.py), [protocol selection](https://github.com/DragonnZhang/claude-tap/blob/64872f527b862906b5944e74b4d155e6cbb4bd44/claude_tap/protocols.py), [capture dummy responses](https://github.com/DragonnZhang/claude-tap/blob/64872f527b862906b5944e74b4d155e6cbb4bd44/claude_tap/pipeline.py).
